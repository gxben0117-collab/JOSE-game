# 戰鬥手感與地形對齊方案

日期：2026-07-18
作者：Claude Code（供 Codex 執行）
背景：動態系統（站立/移動/攻擊 4 幀動畫）已驗證上線且 167 單位全覆蓋。本方案處理下一階段三件事：平滑移動、打擊感工程、地形資料與美術對齊。

## 優先順序總覽

| 順位 | 項目 | 為什麼先做 |
| --- | --- | --- |
| 1 | 地形資料對齊美術 + 標籤顯示策略 | 玩家已實際感到「草地標水」的違和，是正確性問題不是美化 |
| 2 | 平滑移動 | 每天看得到的操作體驗，工程量約 1 天 |
| 3 | 打擊感工程包 | 受擊/死亡目前只有 CSS 位移閃爍，補 hit-stop 與演出 |
| 4 | （可選）受擊/死亡專屬幀 | 動態圖從 6 列擴到 8 列，工程最大，放最後 |

## 一、地形資料對齊美術（修正性問題）

### 現況診斷
- `js/data/map-terrain.js` 由 `scripts/generate-map-terrain.py` 產生，但腳本用的是**固定幾何模板**（如 chapter-01 系列：row2 整排 W、左右三欄 F），與 `assets/maps/*.jpg` 的實際美術內容無關。
- 結果：草原圖上出現整排水滴標籤、沒有樹的格子標「森」。玩家原話：「樹林才標森、有河流才標水，這樣的邏輯才對。」

### 做法（A 案：資料跟著美術走，推薦）
1. 改寫 `generate-map-terrain.py`：對每張 `assets/maps/chapter-XX-YYY-21x10.jpg`，把畫面切成 21×10 格，對每格取樣像素（中心區域平均色 + 色相分布）分類：
   - 藍/青色系佔比高 → `W` 水
   - 深綠且紋理暗 → `F` 森林
   - 橘紅色系 → `R` 熔岩
   - 其他 → `.` 平原
   - `#` 禁行維持現有邊界規則（或由極暗/山壁色判定）
2. 產生後輸出一張「分類疊圖」預覽（把分類結果半透明疊回原圖存 scratch/），人工抽查 60 張中至少 10 張，特別看第一章（玩家正在玩）。
3. 個別誤判用腳本內 per-map override 表修正，不手改輸出檔。
4. 跑 `npm test`；`simulate-tactics.mjs` 確認每張圖仍可通關（水/禁行不可把出生點或必經路徑封死——腳本需加此檢查：部署區到敵方區必須存在可行走路徑）。

### 不採 B 案的原因
B 案（美術跟著資料走，把地形貼片合成到底圖）會讓 60 張精緻大圖變成貼磚感，倒退。

## 二、格子屬性標籤顯示策略

玩家提問：標籤可否全透明或 90% 透明？

### 決策
- **不做全透明**：水/熔岩/禁行影響移動與傷害，完全看不到會踩雷；而且戰棋玩家需要在移動前判斷地形加成。
- **採「平時極淡 + 需要時清楚」**：
  1. 地形對齊美術後（第一節），標籤的資訊多半已由美術本身傳達，預設 opacity 從 0.72 降到 **0.25**。
  2. **選中我方單位時**，其移動/攻擊範圍內的格子標籤升到 opacity 0.9（此時才是玩家真正要讀地形的時刻）。
  3. 熔岩 `R` 與禁行 `#` 例外：任何時候至少 opacity 0.55（危險格必須可見）。
  4. 戰鬥畫面加一顆「地形」小切換鈕（旁邊放現有圖例），開＝全部 0.9，關＝上述淡化邏輯，狀態存 localStorage。
- 相關 CSS：`css/tactics-screens.css` 151、314-316 行的 `.terrain-hint`。

## 三、平滑移動（取消一格一格）

### 現況診斷
`walkUnit()`（js/tactics.js 約 317-333 行）逐格迴圈：每格做一次**全棋盤 render()** → 設 `--walk-x/--walk-y` → `walking` class 跳一下 → `pause(135)`。所以視覺是「跳格子」，且逐格重繪整個棋盤浪費效能。

### 做法
1. `walkUnit` 改為：先算好整條 path 的像素 waypoints（格寬 = `--cell`），**只 render 一次起點**，然後用 Web Animations API（`piece.animate()`）沿 waypoints 做一段連續 translate 動畫：
   - 每格約 100-120ms（乘 `--battle-rate` 倍速），整段 linear、首尾各加一點 ease。
   - 轉向時即時切 `facing-left/right` class（在對應 waypoint 時間點用 animation progress 或分段 animate 處理）。
   - 全程掛 `walking` class 讓走路幀動畫持續播放，結束才移除。
2. 動畫結束後才把 `unit.x/y` 定稿並做最終 `render()`（中途棋格資料已先更新，僅視覺延後）。
3. 敵方 AI 移動與擊退（`knocked`）沿用同一套 waypoint 動畫函式。
4. `pause(135)` 的節奏參數保留為常數，倍速鍵（`setSpeed`）要一起作用。
5. 驗收：手動走 L 型 4 格路徑應是一段連續滑行含轉向；`npm test` 與 `browser-smoke.mjs` 全過（smoke 測試對 `walking` class 的斷言時機可能要跟著調——它在移動中檢查 `motion-walk-*` 動畫，平滑化後此斷言仍應成立）。

## 四、打擊感工程包

現況：受擊=位移+閃白（`hit-impact`）、死亡無專屬演出、無 hit-stop。補：

1. **hit-stop**：命中瞬間全場動畫暫停 60-90ms（暴擊 120ms）。實作：`document.querySelector('.board').style.setProperty('--battle-rate', 0)` 不可行（rate 是乘數），改為 board 加 `.hitstop` class → `*{animation-play-state:paused}`，setTimeout 移除。
2. **鏡頭震動分級**：普攻 2px/暴擊 5px/必殺 8px，只震 board 容器，尊重 `prefers-reduced-motion`。
3. **死亡演出**：倒下（rotate + 下沉 + 灰階漸出）約 450ms，再從棋盤移除；Boss 死亡加白閃 + 慢動作 300ms。
4. **暴擊數字差異化**：更大字 + 橘紅色 + 震動一下（現有 `.damage-number` 加 `.crit` 變體）。
5. 全部效果掛在現有 class 切換點（`damage()`、`removeUnit()`），不動戰鬥邏輯。

## 五、（可選，最後做）受擊/死亡專屬幀

把 168 張動態圖從 6 列（idle/walk/attack × 左右）擴為 8 列（+hit/death）。需要重跑整條生圖產線，工作量最大、收益中等（第四節的 CSS 演出已能蓋掉大半需求）。建議等一~四都上線、玩過再決定要不要做。

## 驗收與收尾

- 每完成一節：`npm test`（66 項回歸）+ `node scripts/browser-smoke.mjs`（需先 `npm.cmd start` 起 4173 伺服器）。
- 地形重生成後，`docs/` 補一張前後對照截圖說明。
- 完成後更新本檔狀態與 CLAUDE.md/Vault 專案索引。
